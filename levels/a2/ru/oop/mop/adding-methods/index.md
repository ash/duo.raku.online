MOP нужен не только, чтобы заглядывать внутрь типов. Он может и **менять** тип, пока программа работает. Метаметод `.^add_method` добавляет в класс новый метод:

```raku
class Empty {
}

Empty.^add_method('greet', method { 'hi' });

say Empty.new.greet; # hi
```

У класса `Empty` совсем нет методов. Потом `Empty.^add_method('greet', …)` добавляет ему метод. Его имя — `greet`. Сам метод — это анонимный `method { … }`. Анонимный значит, что у него нет имени. После этого можно вызывать `.greet` у любого объекта `Empty`. Это работает так, как будто вы написали метод в классе.

Это настоящее метапрограммирование. Метапрограммирование — это код, который работает с кодом. Здесь мы просим метаобъект `Empty` отрастить новый метод. Тот же протокол стоит за вещами, которыми вы уже пользуетесь. Идея такая. Вы пишете `class`, `role`, `has` или `method`. Тогда компилятор строит ваш тип за вас. Он использует MOP-методы, например `.^add_method` и `.^add_attribute`.

Мы говорим «идея» не просто так. Это модель языка. Это не обещание про какой-то один компилятор. Объектная система *определена* через MOP. Реализация — это компилятор для Raku. Правда ли он пропускает каждое объявление через эти метаметоды? И можно ли это увидеть? Каждая реализация решает это сама. Ещё вы можете сами *вызывать* эти метаметоды. По той же причине результат зависит от реализации. Компиляторы могут давать вам разные метаметоды. Эти методы могут и работать по-разному. Код может использовать `.^add_method` и похожие методы. Такой код может работать не одинаково в каждом Raku.

Методы можно добавлять, пока программа работает. Это мощный инструмент. Но он нужен редко. Большинство программ никогда им не пользуются. Но он делает объектную систему Raku открытой. Правила классов тоже написаны с помощью MOP. Поэтому эти правила можно дополнять. Для обычного кода вам нужна другая часть MOP. Вы видели её в прошлой теме. Это метаметоды, которые заглядывают внутрь типов.
