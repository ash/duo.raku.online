MOP потрібен не лише для того, щоб зазирати всередину типів. Він може й **змінити** тип, поки програма працює. Метаметод `.^add_method` додає до класу новий метод:

```raku
class Empty {
}

Empty.^add_method('greet', method { 'hi' });

say Empty.new.greet; # hi
```

Клас `Empty` зовсім не має методів. Потім `Empty.^add_method('greet', …)` додає до нього метод. Його ім'я — `greet`. Сам метод — це анонімний `method { … }`. Анонімний означає, що він не має імені. Після цього можна викликати `.greet` для кожного об'єкта `Empty`. Це працює так, наче ви написали метод у класі.

Це справжнє метапрограмування. Метапрограмування — це код, який працює з кодом. Тут ми кажемо метаоб'єкту `Empty` виростити новий метод. Той самий протокол стоїть за речами, якими ви вже користуєтеся. Ось ідея. Ви пишете `class`, `role`, `has` чи `method`. Тоді компілятор будує ваш тип за вас. Він використовує методи MOP на зразок `.^add_method` та `.^add_attribute`.

Ми кажемо «ідея» не просто так. Це модель мови. Це не обіцянка про якийсь один компілятор. Об'єктну систему *визначено* через MOP. Реалізація — це компілятор для Raku. Чи справді вона пропускає кожне оголошення через ці метаметоди? І чи можна це побачити? Кожна реалізація вирішує це сама. Ви також можете самі *викликати* ці метаметоди. З тієї самої причини результат залежить від реалізації. Компілятори можуть давати вам різні метаметоди. Ці методи також можуть працювати по-різному. Код може використовувати `.^add_method` і схожі методи. Такий код може працювати не однаково в кожному Raku.

Методи можна додавати, поки програма працює. Це потужний інструмент. Але він рідко потрібен. Більшість програм ніколи ним не користуються. Але саме він робить об'єктну систему Raku відкритою. Правила класів теж написані через MOP. Тож ці правила можна доповнювати. Для щоденного коду вам потрібна інша частина MOP. Ви бачили її в попередній темі. Це метаметоди, які зазирають усередину типів.
