Ось один із можливих розв'язків.

## Код

```raku
class Negative is Exception {
    has $.n;

    method message {
        "$.n is negative";
    }
}

sub check($n) {
    Negative.new(n => $n).throw if $n < 0;
    return $n;
}

{
    say check(-5);

    CATCH {
        when Negative {
            say .message;
        }
    }
}

Negative.new(n => -10).throw;
```

🦋 Вихідний код можна знайти у файлі [negative-error.raku](https://github.com/ash/raku-course/blob/master/exercises/oop/custom-exceptions/negative-error.raku).

## Коментарі

1. `Negative is Exception` робить так, що клас можна кидати. Його метод `message` будує текст з атрибута `n`.

1. `check` перевіряє вхідні дані й кидає власний виняток для від'ємного числа. Виняток виходить із `check` і йде до `CATCH` у блоці, який її викликав. Там `when Negative` зіставляється з ним за типом і виводить повідомлення. Це дуже поширене, справжнє застосування власних винятків. Код перевіряє вхідні дані й повідомляє про погані значення винятком власного типу.

1. Навіщо навколо виклику стоїть `{ … }`? Фазер `CATCH` обробляє лише винятки, кинуті в **блоці, який його містить**. Блок об'єднує ризикований `check(-5)` з `CATCH`, який його охороняє. Тож виняток перехоплюється прямо тут, і програма продовжує роботу одразу після блоку. Без блоку `CATCH` охороняв би натомість усю програму. Він перехопив би виняток, але потім програма б просто завершилася. Не було б природного місця, щоб продовжити.

1. Останній `Negative.new(n => -10).throw` показує інший бік цього. Він стоїть **поза** блоком, тож його ніхто не перехоплює. Виняток іде аж до самого верху, і програма гине. Вона виводить повідомлення й трасування стека в стандартний потік помилок. Потім вона завершується з ненульовим статусом. Так стається з будь-яким винятком, який ви не перехоплюєте. І саме тому першому киданню був потрібен `CATCH`, щоб вижити.
