MOP можна використовувати не лише для дослідження типу. Він може й **змінювати** тип, поки програма працює. Метаметод `.^add_method` додає до класу новий метод:

```raku
class Empty {
}

Empty.^add_method('greet', method { 'hi' });

say Empty.new.greet; # hi
```

Клас `Empty` зовсім не має методів. Потім `Empty.^add_method('greet', …)` додає метод на ім'я `greet`, заданий як анонімний `method { … }`. Відтоді кожен об'єкт `Empty` відгукується на `.greet`. Це працює так само, наче ви написали його в класі.

Це справжнє метапрограмування. Ми кажемо метаоб'єкту `Empty` виростити новий метод. Той самий протокол стоїть за можливостями, якими ви вже користувалися. У принципі, це працює так. Коли ви пишете `class`, `role`, `has` чи `method`, компілятор будує ваш тип за вас. Він робить це методами MOP на зразок `.^add_method` та `.^add_attribute`.

Ми кажемо «у принципі», бо це модель мови. Це не обіцянка про якийсь один компілятор. Об'єктну систему *визначено* в термінах MOP. Але чи справді конкретна реалізація пропускає кожне оголошення через ці метаметоди? І чи можна побачити, як вона це робить? Це вирішує кожна реалізація. З тієї самої причини, коли ви самі *викликаєте* ці метаметоди, результат залежить від реалізації. Компілятори можуть пропонувати різні метаметоди, і їхня точна поведінка може відрізнятися. Тож код із `.^add_method` і схожими методами може працювати по-різному в кожному Raku.

Додавання методів під час виконання — потужний інструмент, але він знадобиться вам рідко. Більшість програм ніколи ним не користуються. Але саме він робить об'єктну систему Raku відкритою. Самі правила класів написані через MOP, тож ви можете їх розширювати. У щоденному коді частина MOP, якою ви справді користуватиметеся, — це дослідження типів. Ви бачили ці метаметоди в попередній темі.
